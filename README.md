# OcéEns II

Course evaluation platform built for the EPF engineering school.

## Overview

**OcéEns II** lets program managers, facilitators, campus management and administrators create and manage evaluation *sondages* (surveys) for EPF's programs, and lets students answer them. Responses can be exported, visualised, and summarised by an LLM into *synthèses*. The interface uses EPF's official visual identity, and the application's user interface is in French.

### Tech stack

| Component | Technology |
|-----------|------------|
| **Framework** | FastAPI (Python 3.12) |
| **Authentication** | Microsoft Entra ID (Azure AD) via OAuth 2.0 / MSAL and Microsoft Graph, or a development login (`AUTH_MODE=dev`) |
| **Database** | SQLite (via SQLAlchemy + SQLModel) |
| **Templating** | Jinja2 (server-side rendering) |
| **Frontend** | HTML / CSS / JavaScript, no framework |
| **Server** | Uvicorn |
| **Logging** | Python's standard `logging` module, through Uvicorn's handlers |
| **Exports** | Pandas (CSV) |
| **Verbatim *synthèses*** | Separate daemon calling an LLM (`requests-cache`, `markdown-it-py`) |

## Getting started

These steps take a fresh clone of the `course-2026` branch to a running application in `dev` mode, with no Entra ID and no LLM credentials.

1. Clone the repository on the `course-2026` branch.
2. Copy `.env.example` to `.env`. It ships with `AUTH_MODE=dev`, so no Entra ID credentials are needed; see [Configuration](#configuration) for every variable.
3. Start the application, either:
   - **with Uvicorn**, in a `.venv` virtual environment with Python 3.12: follow [smoke test, step 1](docs/smoke-test.md#1-local-start-no-credentials);
   - **with Docker Compose** (needs a running Docker daemon): follow [smoke test, step 2](docs/smoke-test.md#2-start-with-docker). `docker compose` fails with `env file .env not found` if step 2 was skipped.
4. Open **http://localhost:8000** and sign in from `/dev/login` as any user of the demo data (see [Development login](#development-login)).

On first start, the application creates the tables in the SQLite database (`db_oceens.db`, in the directory set by [`LOCAL_DATABASE_DIR`](#configuration)) and inserts the demo data when the database has no user.

Without an LLM key the application runs normally; only *synthèses* are unavailable (see [smoke test, step 4](docs/smoke-test.md#4-no-llm-key)).

> [!NOTE]
> The Docker image copies the source code at build time and runs Uvicorn without `--reload`: after changing the code, rebuild the image (`--build`). Docker Compose mounts only the database directory and `import/`.

### *Synthèses* daemon

*Synthèses* are generated by a separate process, `summaries_generator_daemon.py`, which polls the database, writes to it and calls an external LLM service. Run it only when needed, in one of these ways:

- run `python summaries_generator_daemon.py` in its own terminal, with the virtual environment's interpreter;
- set [`RUN_SUMMARIES_DAEMON`](#configuration): Uvicorn then starts the daemon as a child process at startup and stops it on shutdown.

### Production server without Docker

`launch.sh` is the start script of the production server: it works in `/home/mde-admin/OceENS`, creates a `venv/` virtual environment if missing, and starts `main.py` (Uvicorn on `0.0.0.0:8000`) and the *synthèses* daemon in two separate `screen` sessions. Leave `RUN_SUMMARIES_DAEMON` unset there, since `launch.sh` already starts the daemon.

## Configuration

The application reads its configuration from environment variables, loaded from a `.env` file at the project root (`load_dotenv()`, which does not override variables already set in the environment). Docker Compose passes the same file to the container through `env_file`; it is never copied into the image.

[`.env.example`](.env.example) is the reference: copy it to `.env` and fill in what you need. This table is the only place in the documentation that describes these variables.

| Variable | Default | Description |
|----------|---------|-------------|
| `AUTH_MODE` | `entra` | `entra`: Microsoft Entra ID. `dev`: [development login](#development-login), with no identity provider. Case-insensitive, surrounding spaces ignored; any other value stops the application at startup (exit code 1). `.env.example` ships `dev`. |
| `DEV_LOGIN_KEY` | *(unset)* | `dev` mode only. When set, every development login must supply it (`key` field), otherwise `401`; when unset or empty, the login is open to anyone. Ignored, with a warning, in `entra` mode. |
| `ALLOWED_DOMAINS` | see description | Comma-separated e-mail domains allowed to sign in, in both modes (`403` otherwise). When unset: `epf.fr,epfedu.fr` in `dev` mode, **no domain at all** in `entra` mode. Adding a user or enrolling students also checks it, with `epf.fr,epfedu.fr` as default. |
| `SECRET_KEY` | *(unset)* | Signs the session cookies. See [the `SECRET_KEY` rule](#the-secret_key-rule). |
| `ENTRA_CLIENT_ID` | *(unset)* | Entra ID application (client) ID. Required with `AUTH_MODE=entra`: if any of the three `ENTRA_*` variables is missing, the application stops at startup (exit code 1). Unused in `dev` mode. |
| `ENTRA_CLIENT_SECRET` | *(unset)* | Entra ID client secret. Same rule as `ENTRA_CLIENT_ID`. |
| `ENTRA_TENANT_ID` | *(unset)* | Entra ID tenant ID. Same rule as `ENTRA_CLIENT_ID`. |
| `REDIRECT_URI` | `https://localhost/auth/callback` | URL Microsoft redirects to after sign-in (`/auth/callback`); its part before `/auth` is also the address users return to after signing out. Unused in `dev` mode. |
| `LOCAL_DATABASE_DIR` | `database/` at the project root | Directory of the SQLite database (`db_oceens.db`), created if missing; a relative path is resolved from the project root. With Docker Compose, the host directory mounted on `/app/database` (default `./database`). |
| `LLM_API_KEY` | *(unset)* | API key of the default LLM provider, *Ollama EPF*. Not read directly: the code reads the variable a provider names in its `api_key_env` field (see [LLM providers](#llm-providers)), and the default provider names `LLM_API_KEY`. When empty or unset, the application runs but *synthèses* are marked with a configuration error. |
| `RUN_SUMMARIES_DAEMON` | *(unset)* | `1`, `true`, `yes` or `on` (case-insensitive): Uvicorn starts the [*synthèses* daemon](#synthèses-daemon) at startup and stops it on shutdown. Leave unset when `launch.sh` runs the daemon. |

In `.env.example`, the `ENTRA_*` variables and `REDIRECT_URI` are commented out, as they are unused in `dev` mode.

### The `SECRET_KEY` rule

`SECRET_KEY` signs the session cookies: anyone who knows it can forge a session for any user, including an admin.

- With `AUTH_MODE=entra`, it is **required**: if it is unset or empty, the application logs `MISSING SECRET_KEY. Required with AUTH_MODE=entra, please check .env` and exits with code 1.
- With `AUTH_MODE=dev`, it is optional: when unset or empty, a random key is drawn at each start (with a warning), so sessions are lost on restart. If a *known* key is set in `dev` mode (shared, copied from an example…), anyone who knows it can forge a session cookie and bypass `DEV_LOGIN_KEY`.

Generate a value with `python -c "import secrets; print(secrets.token_urlsafe(32))"`.

> [!CAUTION]
> Never commit `.env`. It is listed in `.gitignore`, as are `*.db` files and the `database/` directory.

## Roles

- `student`: answers the *sondages* they are enrolled in.
- `program_manager:<code>`: manages the *sondages* of their program(s).
- `facilitator:<code>`: facilitates the *sondages* of their program(s).
- `campus_manager:<campus>`: campus-wide scope.
- `admin`: general administration.

A user can hold several roles, each with its own scope (program codes or campuses separated by `;`).

## Logging

Application logs use Python's standard `logging` module and the `uvicorn` logger, so messages from the application, `auth.py` and `seed.py` share the format, colours and handlers already configured by the server.

Levels are used according to severity:

| Level | Use |
|-------|-----|
| `DEBUG` | Detailed information for development and seeding. |
| `INFO` | Startup, shutdown and normal application operations. |
| `WARNING` | Expected resource missing, or non-blocking situation. |
| `ERROR` / `EXCEPTION` | An operation failed; `logger.exception()` keeps the traceback. |
| `CRITICAL` | Required configuration missing, preventing startup. |

Example:

```python
import logging

logger = logging.getLogger("uvicorn")

logger.info("Operation complete")

try:
    risky_operation()
except Exception:
    logger.exception("Operation failed")
```

New diagnostics should use the appropriate logger rather than `print()`. The application level is currently set to `DEBUG` in `core/dependencies.py`. Application logs go through Uvicorn's handler, usually written to `stderr`; to capture them separately, redirect it, for instance with `2> error.log`.

## LLM providers

Verbatim *synthèses* are generated by an LLM. The provider is **configurable from the interface** (`/backend/providers`, admin only), without touching the code. The default provider is **Ollama EPF** (`https://locallm.mde.epf.fr/ollama`, model `gemma4:26b`), created automatically at startup if missing.

### Supported API types

| `api_type` | Covers |
|------------|--------|
| `ollama`    | Ollama servers (local, EPF, third-party) |
| `openai`    | OpenAI **and any OpenAI-compatible endpoint**: vLLM, Groq, Mistral, LM Studio… |
| `anthropic` | Claude API (Anthropic) |

### Security principle: no key in the database

The SQLite database is not encrypted and ends up in backups. **No API key is stored in it.** The `llm_providers` table only holds the *name* of the environment variable (`api_key_env`, e.g. `OPENAI_API_KEY`); the value stays in the environment and is only resolved at call time. This name is checked against an allow-list (`LLM_*` or `*_API_KEY`) so that it cannot point to a system secret (`SECRET_KEY`, `ENTRA_CLIENT_SECRET`…).

### Adding a provider

1. **Add the key to `.env`** under a compliant name (`LLM_*` or `*_API_KEY`):

   ```env
   OPENAI_API_KEY=sk-...
   ```

2. **Restart the application and the *synthèses* daemon**: each process reads `.env` only at startup.

3. **Create the provider** in `/backend/providers` → *+ Nouveau fournisseur*: fill in the name, API type, base URL, environment variable name (`OPENAI_API_KEY`) and a default model. The **key present / missing** indicator confirms that the variable is loaded. The **Tester** button checks that the URL and key respond, then sends a one-token generation to confirm that the account can actually generate (see below).

4. **Link a prompt** to the provider: in `/backend/prompts`, a `<select>` chooses a prompt's provider. A prompt without a provider (`provider_id` NULL) falls back to Ollama EPF.

> [!NOTE]
> A provider referenced by at least one prompt cannot be deleted, so as not to break those prompts' configuration.

### Exhausted credit and other provider errors

Each provider reports failures in its own format: exhausted credit is a `429 insufficient_quota` at OpenAI, but a `400 "Your credit balance is too low"` at Anthropic. `services/llm_client.py` normalises these responses into categories (`quota`, `rate_limit`, `auth`, `model`, `server`) and derives a readable message from them, in French, for example:

> ⚠️ Crédit ou quota épuisé chez le fournisseur : la clé est valide mais le
> compte ne peut plus générer. Rechargez le compte ou choisissez un autre
> fournisseur. (fournisseur OpenAI, modèle gpt-4o-mini, HTTP 429)

This message is written to `Summary.metadata_text` instead of the raw JSON, so it is visible directly in the interface when a *synthèse* fails. The provider's raw response stays in the daemon logs for diagnosis.

> [!IMPORTANT]
> The **Tester** button does not just list the models: at OpenAI as at Anthropic, `GET /v1/models` still answers perfectly well with a zero balance. A one-token generation ping (negligible cost) is therefore sent next: it is the only way to spot exhausted credit **before** starting a *synthèses* campaign.

## Cost of *synthèses*

The cost of each *synthèse* is **measured, not estimated**. At generation time, the daemon records the token counts returned by the provider (`Summary.input_tokens`, `output_tokens`, `model_used`): it is the only chance to capture them, as no API lets you ask for them afterwards. The amount is then obtained by combining these counts with the price list.

> [!NOTE]
> This replaces the former `llm-utils/token-counting/` scripts, which counted the tokens of the **repository's source code** and multiplied them by a hard-coded rate. That measure said nothing about the application's actual spending. Tracking now covers the calls actually billed.

### Price list: `/backend/llm/prices`

Prices live in the database (table `llm_model_prices`) and **all amounts are in euros**. Each price has two components, added together:

- a **flat cost per generation**, given as a range (`flat_cost_min` / `flat_cost_max`), for models whose cost is not measured in tokens; an exact cost is entered with min = max;
- a **price per million tokens**, input and output, for commercial providers billing by usage.

Prices can be entered in EUR or USD; USD amounts are converted at the USD → EUR rate stored in the database (default 0.92), editable on the same page. A new rate only applies to prices entered afterwards: prices already converted do not change.

Prices are editable from the administration: no release is needed to follow a price change, nor to cover a provider added locally. These are pre-filled at startup (`seed_model_prices`, idempotent: a price corrected by hand is never overwritten):

| Model | Flat cost per generation | Input / output per million tokens |
| --- | --- | --- |
| `gemma4:26b` (Ollama EPF, self-hosted) | €0.02 to €0.05 | €0 / €0 |
| `claude-opus-5` | none | $5.00 / $25.00, converted to euros |
| `claude-sonnet-5` | none | $3.00 / $15.00, converted to euros |
| `claude-haiku-4-5` | none | $1.00 / $5.00, converted to euros |

The self-hosted model is not free: the flat range covers GPU, electricity and server depreciation. Prices for other providers (OpenAI, Mistral, Groq…) **must be entered**: they are not guessed. A provider-specific price takes precedence over a generic price for the same model name.

### Where to see costs

| Where | What |
| --- | --- |
| `/backend/llm/costs` | Total cost, broken down per *sondage* and per model (admin) |
| 💰 button on a *sondage* row | Cost of that *sondage*'s *synthèses* (`GET /api/surveys/{survey_id}/cost`) |

### What is not priced

A *synthèse* cannot be priced when its token counts are missing (generated before this feature, or a provider that does not return them) or when its model has no recorded price. It is then **counted separately**, never estimated or set to zero: an invented amount would be worse than a missing one, since it would be displayed with the authority of a real amount. The screens say explicitly when a total is partial.

This is different from a **zero** cost, which is a known amount, not an unknown one.

> [!IMPORTANT]
> Tracking starts when the feature goes live: *synthèses* generated before have no counts in the database and cannot be priced retroactively.

## Authentication (OAuth 2.0)

With `AUTH_MODE=entra`, authentication relies on **Microsoft Entra ID** through the MSAL library:

```
1. The user clicks "Connexion" (/login)
   → FastAPI generates a random state (UUID, CSRF protection) and stores it in the session
   → Redirect to the Microsoft login page

2. The user signs in at Microsoft
   → Microsoft redirects to /auth/callback with a code + state

3. The server exchanges the code for an access token
   → Fetches the user's details from Microsoft Graph
   → Checks the e-mail domain against ALLOWED_DOMAINS
   → Gets or creates the user in the database (an unknown user becomes a student)
   → Stores {name, email} in the session
   → Redirects to /, which sends the user to their dashboard

4. On sign-out (/logout)
   → Clears the session and cookies
   → Signs out at Microsoft
   → Returns to the home page
```

Authentication alone allows no business action: each route then checks the role and scope (program or campus) via `require_roles()` and its related helpers.

## Development login

To work on a fork without an Azure application, the **development login** (`AUTH_MODE=dev`) lets you sign in as any user, with no proof of identity. It must **never** be used in production. Its variables (`AUTH_MODE`, `DEV_LOGIN_KEY`, `ALLOWED_DOMAINS`, `SECRET_KEY`) are described in [Configuration](#configuration).

In `dev` mode, the session cookie is no longer restricted to HTTPS (`http://localhost` works), `/login` redirects to `/dev/login`, `/auth/callback` does not exist and `/logout` clears the session then redirects to `/`. A warning is logged at startup. A red banner that cannot be closed is shown at the top of every page that includes the shared header: it recalls the signed-in address, offers "Changer d'utilisateur" (`/dev/login`) and says "accès ouvert à tous" when `DEV_LOGIN_KEY` is not set.

`POST /dev/login` expects a form with `email`, `name` (optional) and `key` (if `DEV_LOGIN_KEY` is set). The user is fetched or created as on return from Entra: an unknown e-mail becomes a new student. Without `name`, the display name is built from the e-mail (`bob.leponge@epfedu.fr` → "Bob Leponge"). A new sign-in replaces the session: that is how you switch users.

In a browser, `GET /dev/login` lists the users in the database, grouped by role name without scope (a user with no role appears under `student`, a user with several roles under each of them). A click signs in as the chosen user; a free field lets you use another address, with an optional name. If `DEV_LOGIN_KEY` is set, a single key field is shown and used for every sign-in on the page; the key is never stored in the session. Come back to this page to switch users.

```bash
AUTH_MODE=dev DEV_LOGIN_KEY=my-key uvicorn main:app

# Sign in as the seed's admin; -c saves the session cookie
curl -i -c cookies.txt \
  -d email=antoine.gademer@epf.fr -d key=my-key \
  http://localhost:8000/dev/login

# Reuse the cookie (-b) for the next requests
curl -b cookies.txt -c cookies.txt -L http://localhost:8000/
```

> [!WARNING]
> A known `SECRET_KEY` defeats `DEV_LOGIN_KEY`: see [the `SECRET_KEY` rule](#the-secret_key-rule).

## Notable features

### Teacher analytics

The `/dashboard/teachers/analytics` route (`campus_manager`, `program_manager`) aggregates the satisfaction score per `(teacher, sondage)` from `QCU_Satisfaction` answers that have a non-empty `Answer.teacher`, within the user's scope. The teacher list is sorted with `teacher_sort_key()`, case- and accent-insensitive, and can be filtered by school year, semester, program and teacher.

### Teacher filter in the visualisation

A client-side selector filters the visualisation without reloading: only the chosen teacher's blocks remain visible, module rows left with no visible teacher are hidden, and so are the sections that are not module / teacher (`ME`) sections, such as Campus and Formation in the demo templates. The page reads `?teacher=<name>` on load to pre-filter itself; links from the analytics page pass this parameter, so clicking a teacher's score opens their view directly.

### *Sondages* imported from Excel

*Sondages* loaded by `survey_loader_from_xlsx.py` have no `QCU_Attendance` question: `services/visualisation_data.py` then uses `satisfaction_responses_count` as the fallback denominator for the teacher score. Teacher names are normalised with `.title()` both at import and at aggregation, to merge case variants (`"GADEMER Antoine"` and `"Gademer Antoine"` are a single entry). In the visualisation template, questions are displayed in `question_id` order.

### Campus management scope

The `campus_manager` dashboard only shows closed *sondages* with at least one respondent. The link to the questionnaire and the QR code are hidden there (`can_view_survey_link=False`): this role reads results without distributing *sondages*. The `{% if can_view_survey_link | default(true) %}` guard leaves the other dashboards unchanged.

### Cleaning up orphan students

When a *sondage* is deleted, students who are no longer attached to **any other** *sondage* are deleted too, to avoid piling up unused accounts (`services/helpers.py`, `_delete_orphan_students`). A safeguard protects users with a privileged role (`admin`, `program_manager`, `facilitator`, `campus_manager`): a teacher or manager who answered a *sondage* is never deleted.

### Adding a user by e-mail

The "Utilisateurs" tab of the administrator dashboard has a **"+ Ajouter un utilisateur"** button: an e-mail is enough to create the account, with the `student` role by default (`POST /api/users`, admin only). The e-mail is validated (format + allowed domain) and duplicates are refused.

## Deployment checklist

- [ ] `.env` created with the real Entra ID credentials and `REDIRECT_URI`
- [ ] `AUTH_MODE` unset or `entra`
- [ ] A dedicated `SECRET_KEY` (see [the `SECRET_KEY` rule](#the-secret_key-rule))
- [ ] `ALLOWED_DOMAINS` set: in `entra` mode, no domain is allowed when it is unset
- [ ] Valid SSL certificate (Let's Encrypt or equivalent): outside `dev` mode, the session cookie is HTTPS-only
- [ ] Database present (`db_oceens.db` in `LOCAL_DATABASE_DIR`) or Docker volume mounted
- [ ] Environment variables secured, including LLM keys such as `LLM_API_KEY`
- [ ] **Docker Compose**: `.env` loaded through `env_file`, never copied into the image; `LOCAL_DATABASE_DIR` pointing to the right database directory
- [ ] *Synthèses* daemon running if LLM *synthèses* are used
